# Conqueror Platform — Hub (Design Spec 3)

Status: REVIEWED 2026-10-10 · Date: 2026-10-10 · Depends on: Spec 0, Spec 1

The hub is the **optional** rich control centre: a standalone server on the LAN. The tank never depends on it.

## 1. Stack and deployment
- **Backend:** Node.js + TypeScript.
- **Web UI:** React + TypeScript, served by the hub.
- **Storage:** SQLite (single file) + video files on disk (MP4 via ffmpeg).
- **Deployment:** Docker image (multi-arch amd64 + arm64) and `docker-compose.yml` (hub + AI engine), data in a mounted volume; also runnable natively for development.
- **Protocol types** generated from `protocol/` (shared with the AI engine).

## 2. Scope
- **Many tanks, one local site** (hobby). All data keyed by tank ID.
- Users: **one admin login** + optional view-only **guest**. No multi-user accounts, no cloud, no internet exposure.

## 3. Modules

| Module | Responsibility |
|---|---|
| **Tank manager** | mDNS discovery (`_conqueror._tcp`); add/forget tanks; **pairing** (Spec 1 §3: admin password once → mints `hub-admin`, `hub-human`, `hub-ai` keys); per tank one MJPEG connection and one WS **per role in use** (human always, ai while the AI engine is attached, admin on demand); auto-reconnect; online/offline; clock-offset estimation via `ping`/`pong` |
| **Fan-out** | re-shares each tank's telemetry, events and video to any number of browsers and to the AI engine; one tank stream regardless of viewer count |
| **Control gateway** | forwards browser commands on the `hub-human` connection, AI-engine commands on `hub-ai`, admin actions (settings, calibration, keys, camera config) on `hub-admin`; the tank arbitrates priority. Browser STOP always forwarded |
| **Auth** | admin login (+ guest), session cookies; tank keys never leave the server |
| **History** | telemetry at full rate for 7 days, downsampled to 1 Hz for 90 days; queries for graphs |
| **Recording** | per-session MP4 + telemetry track (aligned by `tank_ms` → hub time offset), snapshots; disk cap, oldest-first deletion |
| **Missions** | create/edit waypoint missions on the map; push to the tank (`/api/missions`) and run |
| **Events/logs** | unified timeline: tank events, control changes, alarms, AI decisions |
| **AI API** | the interface the AI engine uses (§5) |
| **Camera benchmark** | runs a fixed test procedure and stores a report (fps, end-to-end latency, low-light noise, detection confidence on a test scene, depth quality, FOV coverage) for comparing cameras before/after upgrades |

## 4. Web UI screens
1. **Fleet overview** — all tanks: online, battery, owner, flags, thumbnails.
2. **Drive** — live video; left joystick (drive, smooth arcs), right joystick (camera, spring-home), **phone-tilt steering** option (browser DeviceOrientation, sends the same `drive` values); quick buttons (stop, camera lock, home, sounds, LED, obstacle brake, child-play envelope, release to AI); live gauges (battery, heading, distance/TTC, speed, flags).
3. **Map** — pose track, home, waypoint mission editor, AI-reported objects.
4. **History** — graphs over time, event timeline.
5. **Recordings** — playback with synchronised telemetry overlay; snapshot gallery.
6. **Tank settings** — calibration wizards (Spec 2 §A10), safety limits, sounds/audio mode, servo limits/trim, keys, camera config, links to the tank's WiFi/OTA page, camera benchmark.
7. **AI** — engine status and tier, controlled tanks, active skill, decision log, LLM/perception config, command box (text + voice).

Child-play start flow: the UI asks "Adult present? Track guards fitted? Flat area?" before enabling the `child_play` envelope and play skills.

## 5. AI engine interface (hub ↔ AI engine)
- AI engine connects to the hub over a local WebSocket with a hub-issued service token.
- Receives: per-tank telemetry/events (same JSON as Spec 1 §6) with hub-time-aligned timestamps; video via the hub's re-stream URL (MJPEG with `X-Timestamp`); user commands (text, voice transcripts) addressed to a tank.
- Sends: tank commands (Spec 1 §5, forwarded with `hub-ai` → AI priority enforced by the tank); AI status, decisions and detected objects (for the map/log); speech output requests (TTS played in the browser/phone).
- The hub never blocks driving on the AI; AI disconnect = AI owner silence → the tank's deadman/handback rules apply.

## 6. Failure behaviour
- Tank offline → tile greyed, commands rejected, reconnect with backoff.
- Hub restart → reconnect to known tanks; no tank state is owned by the hub (pose/missions live on the ESP32).
- AI engine down → AI page shows offline; manual control unaffected.

## 7. REST API (v1)

### 7.1 Conventions
- Base path **`/api/v1`**; JSON only (`application/json`; errors `application/problem+json`).
- Resource nouns, plural, kebab-case paths: `/tanks/{tankId}/surface-profiles`.
- Fields `camelCase`; timestamps ISO-8601 UTC (`2026-10-10T12:00:00.000Z`); units in field names (`distanceCm`, `durationMs`).
- Methods: `GET` read (safe) · `POST` create / trigger action · `PUT` full replace · `PATCH` partial update (JSON Merge Patch) · `DELETE` remove.
- Status codes: `200` OK · `201` Created (+`Location`) · `202` Accepted (long-running → operation resource) · `204` No Content · errors per §8.
- **Pagination:** cursor-based `?limit=50&cursor=…` → `{ "items": [...], "nextCursor": "…" | null }`; stable sort by `createdAt` then id.
- **Filtering/sorting:** `?from=&to=` (time ranges), `?kind=` (events), `?sort=-createdAt`.
- **Optimistic concurrency** for editable resources (settings, missions, profiles): `ETag` on GET, `If-Match` required on PUT/PATCH/DELETE → `412` on mismatch.
- **Idempotency:** `POST` that triggers actions accepts `Idempotency-Key` (24 h replay window).
- **Long-running operations** (calibration, benchmark, export): `202` + `Location: /api/v1/operations/{opId}` → `{ id, kind, status: queued|running|succeeded|failed|cancelled, progressPct, result?, error? }`; progress also pushed over WS.
- **Real-time driving is WebSocket only** (§7.3); REST is for state, history, configuration and discrete actions.
- Every response carries `X-Request-Id` (generated or propagated from the request).
- OpenAPI 3.1 generated from route schemas: `GET /api/v1/openapi.json`; interactive docs at `/api/docs` (admin).

### 7.3 WebSocket `/api/v1/ws` (browsers and the AI engine)
- Authenticated by session cookie (browsers) or service token (AI engine).
- Envelope identical to the tank protocol (`t`, `id`, `seq`): `subscribe{tankId, streams}`, `cmd{tankId, …protocol command}`, `ack`/`nack`, `tf`/`ts`/`ev` (tank-tagged), `op` (operation progress), `ai` (decisions/status).
- Backpressure: per-client latest-value buffers for telemetry (drop stale), bounded queues for events; slow clients never delay the tank link. STOP bypasses all queues.

## 8. Error handling

### 8.1 Error classes (custom hierarchy)
```ts
abstract class AppError extends Error {
  abstract readonly code: ErrorCode;      // stable machine code (registry §8.3)
  abstract readonly httpStatus: number;
  readonly details?: Record<string, unknown>;   // safe-to-expose context
  readonly cause?: unknown;                     // internal, never exposed
}
```
| Class | HTTP | Typical codes |
|---|---|---|
| `ValidationError` | 422 | `invalid_body`, `invalid_query`, `invalid_command` (field errors in `details.fields`) |
| `BadRequestError` | 400 | `malformed_json` |
| `UnauthenticatedError` | 401 | `not_logged_in`, `session_expired` |
| `ForbiddenError` | 403 | `role`, `guest_read_only` |
| `NotFoundError` | 404 | `tank_not_found`, `mission_not_found`, … |
| `ConflictError` | 409 | `already_paired`, `not_owner`, `envelope_locked`, `busy` |
| `PreconditionFailedError` | 412 | `etag_mismatch` |
| `RateLimitedError` | 429 | `rate_limited` |
| `TankRejectedError` | 409/422 | maps tank nack codes: `blocked`, `unavailable`, `envelope`, `invalid` |
| `TankOfflineError` | 503 | `tank_offline`, `body_offline` |
| `UpstreamTimeoutError` | 504 | `tank_timeout`, `ai_timeout` |
| `InternalError` | 500 | `internal` (wraps anything unexpected) |

Rules:
- Application/domain code **throws `AppError` subclasses** for expected failures; adapters convert foreign errors (WS, SQLite, ffmpeg) into `AppError`s with the original as `cause`.
- **One central error handler** (HTTP + WS) maps errors to the response; anything not an `AppError` → `InternalError`, logged at `error` with stack, response without internals.
- Async safety: no floating promises (lint), every route handler async-wrapped; `process.on('unhandledRejection'|'uncaughtException')` → log `fatal` + graceful shutdown (container restarts it).
- Validation errors are produced only by schema validation at the edge (zod schemas generated from `protocol/`).

### 8.2 Error response (RFC 9457 Problem Details)
```json
{
  "type": "https://conqueror.local/errors/tank-offline",
  "title": "Tank offline",
  "status": 503,
  "code": "tank_offline",
  "detail": "Tank conqueror-a1b2 has not responded for 12 s.",
  "instance": "/api/v1/tanks/a1b2/commands",
  "requestId": "01JA…",
  "details": { "tankId": "a1b2", "lastSeen": "2026-10-10T12:00:00Z" }
}
```
WS errors use the protocol `nack` with the same `code` values.

### 8.3 Error code registry
- Single list in `protocol/errors` (shared by tank nack codes, hub, AI engine): `code`, HTTP status, title, description.
- Codes are **stable API**: never renamed, only added/deprecated.

## 9. Logging
- **pino** structured JSON to stdout (Docker) + rotating file in the data volume (7 days / 200 MB cap); queryable via `GET /logs`.
- Standard fields: `time`, `level`, `msg`, `service:"hub"`, `version`, `requestId`, `tankId`, `userRole`, `route`, `method`, `status`, `durationMs`, `err{code,message,stack}`.
- **Levels:** `fatal` process cannot continue · `error` request/operation failed unexpectedly · `warn` degraded (tank reconnecting, slow client dropped, timeout) · `info` lifecycle & state changes (pairing, connect/disconnect, owner change, calibration result, recording start/stop) · `debug` detailed flow (off by default) · `trace` protocol frames (dev only).
- One access-log line per HTTP request (`info`, `debug` for `/healthz` and `/metrics`).
- **Never logged:** passwords, tank keys, session cookies, AI API keys (pino `redact` list); telemetry streams (stored in history, not logs).
- Correlation: `X-Request-Id` → log context → forwarded as the protocol command `id` → tank ack/nack logs carry it back.
- Per-module child loggers (`tankManager`, `recording`, …); log level changeable at runtime by admin (`PATCH /system/log-level`).
