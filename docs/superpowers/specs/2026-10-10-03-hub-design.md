# Conqueror Platform — Hub (Design Spec 3)

Status: REVIEWED 2026-10-10 · Date: 2026-10-10 · Depends on: Spec 0, Spec 1

The hub is the **optional** rich control centre: a standalone server on the LAN. The tank never depends on it.

## 1. Stack and deployment
- **Backend:** Node.js + TypeScript, **NestJS on the Fastify adapter** (house standard).
- **Web UI:** React + TypeScript, served by the hub.
- **Storage:** SQLite (single file) + video files on disk (MP4 via ffmpeg).
- **Deployment:** Docker image (multi-arch amd64 + arm64) and `docker-compose.yml` (hub + AI engine), data in a mounted volume; also runnable natively for development.
- **Protocol types** generated from `protocol/` (shared with the AI engine).

## 2. Scope
- **Many tanks, one local site** (hobby). All data keyed by tank ID.
- Users: **one admin login** + optional view-only **guest**. No multi-user accounts, no cloud, no internet exposure.

## 3. Modules

| Module | Responsibility |
|---|---|
| **Tank manager** | mDNS discovery (`_conqueror._tcp`); add/forget tanks; **pairing** (Spec 1 §3: admin password once → mints `hub-admin`, `hub-human`, `hub-ai` keys); per tank one MJPEG connection and one WS **per role in use** (human always, ai while the AI engine is attached, admin on demand); auto-reconnect; online/offline; clock-offset estimation via `ping`/`pong` |
| **Fan-out** | re-shares each tank's telemetry, events and video to any number of browsers and to the AI engine; one tank stream regardless of viewer count |
| **Control gateway** | forwards browser commands on the `hub-human` connection, AI-engine commands on `hub-ai`, admin actions (settings, calibration, keys, camera config) on `hub-admin`; the tank arbitrates priority. Browser STOP always forwarded |
| **Auth** | admin login (+ guest), session cookies; tank keys never leave the server |
| **History** | telemetry at full rate for 7 days, downsampled to 1 Hz for 90 days; queries for graphs |
| **Recording** | per-session MP4 + telemetry track (aligned by `tank_ms` → hub time offset), snapshots; disk cap, oldest-first deletion |
| **Missions** | create/edit waypoint missions on the map; push to the tank (`/api/missions`) and run |
| **Events/logs** | unified timeline: tank events, control changes, alarms, AI decisions |
| **AI API** | the interface the AI engine uses (§5) |
| **Camera benchmark** | runs a fixed test procedure and stores a report (fps, end-to-end latency, low-light noise, detection confidence on a test scene, depth quality, FOV coverage) for comparing cameras before/after upgrades |

## 4. Web UI screens
1. **Fleet overview** — all tanks: online, battery, owner, flags, thumbnails.
2. **Drive** — live video; left joystick (drive, smooth arcs), right joystick (camera, spring-home), **phone-tilt steering** option (browser DeviceOrientation, sends the same `drive` values); quick buttons (stop, camera lock, home, sounds, LED, obstacle brake, child-play envelope, release to AI); live gauges (battery, heading, distance/TTC, speed, flags).
3. **Map** — pose track, home, waypoint mission editor, AI-reported objects.
4. **History** — graphs over time, event timeline.
5. **Recordings** — playback with synchronised telemetry overlay; snapshot gallery.
6. **Tank settings** — calibration wizards (Spec 2 §A10), safety limits, sounds/audio mode, servo limits/trim, keys, camera config, links to the tank's WiFi/OTA page, camera benchmark.
7. **AI** — engine status and tier, controlled tanks, active skill, decision log, LLM/perception config, command box (text + voice).

Child-play start flow: the UI asks "Adult present? Track guards fitted? Flat area?" before enabling the `child_play` envelope and play skills.

## 5. AI engine interface (hub ↔ AI engine)
- AI engine connects to the hub over a local WebSocket with a hub-issued service token.
- Receives: per-tank telemetry/events (same JSON as Spec 1 §6) with hub-time-aligned timestamps; video via the hub's re-stream URL (MJPEG with `X-Timestamp`); user commands (text, voice transcripts) addressed to a tank.
- Sends: tank commands (Spec 1 §5, forwarded with `hub-ai` → AI priority enforced by the tank); AI status, decisions and detected objects (for the map/log); speech output requests (TTS played in the browser/phone).
- The hub never blocks driving on the AI; AI disconnect = AI owner silence → the tank's deadman/handback rules apply.

## 6. Failure behaviour
- Tank offline → tile greyed, commands rejected, reconnect with backoff.
- Hub restart → reconnect to known tanks; no tank state is owned by the hub (pose/missions live on the ESP32).
- AI engine down → AI page shows offline; manual control unaffected.

## 7. REST API (v1) — NestJS house standard

### 7.1 Framework and global setup (`src/main.ts`)
- **NestJS on the Fastify adapter**; WebSocket gateway via `@nestjs/platform-ws`.
- Global prefix `api/v1`; Helmet; compression; CORS allowlist (hub origin + configured app origins); graceful shutdown hooks (close tank links, finish recordings).
- **Validation:** schemas are **zod, generated from `protocol/`**, exposed as DTO classes via `nestjs-zod` (`createZodDto`) with a global `ZodValidationPipe` (unknown fields rejected; query strings coerced). Hub-only DTOs (login, filters) are hand-written zod DTOs in the module's `dto.ts`.
- Swagger/OpenAPI (via `nestjs-zod` integration) in non-production only, at `/api/docs`.
- OpenTelemetry SDK initialised **before any other import** (§10).

### 7.2 Controllers and routes
- Resource-named controllers, guard at class level (`@UseGuards(SessionAuthGuard)`), role guards per route (`@Roles('admin')`).
- Nested resources as path segments: `tanks/:tankId/missions/:missionId/run`; params parsed inline (`ParseUUIDPipe`, custom `ParseTankIdPipe`).
- `@CurrentUser()` decorator for the session principal (admin / guest).
- Methods: `GET` read · `POST` create/action · `PUT` replace · `PATCH` partial · `DELETE`.
- **Optimistic concurrency** on editable resources (settings, missions, surface profiles): `ETag` / `If-Match` → `412` on mismatch.
- **Idempotency:** action `POST`s accept `Idempotency-Key` (24 h replay window).
- **Long-running operations** (calibration, benchmark): `202` + operation resource `/operations/:opId` (`status: queued|running|succeeded|failed|cancelled`, `progressPct`, `result`, `error`); progress also pushed over WS.
- **Driving is WebSocket only**; REST is for state, history, configuration, discrete actions.

### 7.3 Response envelope (global `TransformInterceptor`)
```jsonc
// single value
{ "success": true, "data": { … }, "requestId": "…", "timestamp": "2026-10-10T12:00:00.000Z" }
// page-based list (small collections: missions, recordings, snapshots, keys, profiles)
{ "success": true, "data": [ … ], "pagination": { "page": 1, "limit": 20, "total": 134, "totalPages": 7 }, "requestId": "…", "timestamp": "…" }
// cursor-based list (time-series: telemetry, events, logs, AI decisions)
{ "success": true, "data": [ … ], "pagination": { "limit": 100, "nextCursor": "…" }, "requestId": "…", "timestamp": "…" }
```
- Services return `PaginatedResult<T>` or `CursorResult<T>`; the interceptor reshapes.
- **Unwrapped pass-through:** `204`, health checks, `/metrics`, WebSocket, MJPEG relay, video range requests, file downloads.
- Fields `camelCase`; timestamps ISO-8601 UTC; units in names (`distanceCm`, `durationMs`).

### 7.5 WebSocket gateway `/api/v1/ws` (browsers and the AI engine)
- Auth: session cookie (browsers) or service token (AI engine) at upgrade.
- Envelope identical to the tank protocol (`t`, `id`, `seq`): `subscribe{tankId, streams}`, `cmd{tankId, …}`, `ack`/`nack`, `tf`/`ts`/`ev` (tank-tagged), `op` (operation progress), `ai` (decisions/status).
- `nack` carries the same `code` + `reason` as REST errors (§8).
- Backpressure: per-client latest-value buffers for telemetry (drop stale), bounded event queues; slow clients never delay the tank link; **STOP bypasses all queues**.

## 8. Error handling

### 8.1 Exception hierarchy
```ts
export abstract class BusinessException extends HttpException {
  constructor(
    message: string,
    status: HttpStatus,
    public readonly isOperational: boolean,
    public readonly reason: ErrorReason,                 // symbolic, e.g. TANK_OFFLINE
    public readonly details?: Record<string, unknown>,   // safe to expose
    options?: { cause?: unknown },                       // internal, never exposed
  ) { super({ message, reason, details }, status, options); }
  get code(): ErrorCode { return errorRegistry[this.reason].code; } // numeric, e.g. TANK_2003
}
```
| Class | HTTP | isOperational |
|---|---|---|
| `ValidationError` | 400 | true |
| `UnauthorizedError` | 401 | true |
| `ForbiddenError` | 403 | true |
| `NotFoundError` | 404 | true |
| `ConflictError` | 409 (not owner, envelope locked, already paired, busy) | true |
| `PreconditionFailedError` | 412 (ETag mismatch) | true |
| `PayloadTooLargeError` | 413 | true |
| `UnprocessableError` | 422 (tank rejected: blocked, unavailable, invalid command) | true |
| `RateLimitError` | 429 | true |
| `ServiceUnavailableError` | 503 (tank offline, body offline, AI offline) | true |
| `GatewayTimeoutError` | 504 (tank/AI timeout) | true |
| `InternalError` | 500 | **false** |
- Adapters wrap foreign errors (WS, SQLite, ffmpeg, mDNS) into these with `cause`.
- Anything that is not a `BusinessException` → `InternalError` (non-operational).

### 8.2 Error code registry (`protocol/errors`, generated for tank, hub, AI engine)
- Each entry: **`code`** (numeric, stable, never reused) + **`reason`** (symbolic) + HTTP status + message template.
- Domain ranges: `AUTH_1xxx` · `TANK_2xxx` (pairing, connection, offline) · `COMMAND_3xxx` (tank rejections: `NOT_OWNER`, `BLOCKED`, `UNAVAILABLE`, `ENVELOPE_LOCKED`, `BODY_OFFLINE`, `INVALID_COMMAND`, …) · `MISSION_4xxx` · `RECORDING_5xxx` · `CALIBRATION_6xxx` · `AI_7xxx` · `SETTINGS_8xxx` · `SYSTEM_9xxx`. A new domain reserves the next range.
- **The generator enforces** unique codes, codes inside their domain range, and no reuse of retired codes (retired list kept in the registry).
- Tank `nack`s carry the same `code` + `reason` (Spec 1 §4).

### 8.3 Global exception filter → error envelope
```json
{
  "success": false,
  "error": {
    "code": "TANK_2003",
    "reason": "TANK_OFFLINE",
    "message": "Tank conqueror-a1b2 has not responded for 12 s",
    "requestId": "a1b2…",
    "timestamp": "2026-10-10T12:00:00.000Z",
    "path": "/api/v1/tanks/a1b2/commands",
    "details": { "tankId": "a1b2", "lastSeenAt": "2026-10-10T11:59:48.000Z" },
    "validationErrors": [{ "field": "by", "message": "must be between -360 and 360" }],
    "stack": "… (non-production only)"
  }
}
```
- One filter for HTTP and WS (WS emits `nack` with `code`, `reason`, `message`, `details`).
- Logs: operational 4xx at `warn`, non-operational at `error` with stack; records the exception on the active OTel span.
- Same `requestId` as the success envelope.
- Process-level `unhandledRejection` / `uncaughtException` → log `fatal`, graceful shutdown (container restarts).

## 9. Logging
- **nestjs-pino** replaces Nest's logger app-wide; services use injected `PinoLogger` (or `new Logger(Class.name)` for one-offs).
- **Correlation ID:** middleware sets the request ID — active OTel trace ID → incoming `X-Request-ID` / `x-trace-id` / `x-correlation-id` → new UUID; echoed as `X-Request-ID`; stored in **AsyncLocalStorage** so non-request code (tank manager, recording, WS handlers) can read it; pino `genReqId` reuses it.
- **Closed gap:** an interceptor running after guards enriches the AsyncLocalStorage context with `userRole` and **`tankId`** (from route params / WS messages); a context-aware child logger adds them to **every** log line, including ad-hoc ones.
- **Command correlation:** the request ID is forwarded as the tank protocol command `id`; tank ack/nack logs carry it back.
- **Redaction:** passwords, tank keys, session cookies, `Authorization`, AI API keys.
- **Transport:** production JSON to stdout + size-rotated files in the data volume (`combined.*.log`, `error.*.log`, 5 files); development `pino-pretty`. Level `info` (prod) / `debug` (dev), changeable at runtime by admin.
- **Noise control:** health checks and `/metrics` excluded from request-completed lines; telemetry is never logged (it is stored in history).
- **Level policy:** `fatal` process cannot continue · `error` non-operational failure · `warn` operational failure / degraded (tank reconnecting, slow client dropped, timeout) · `info` lifecycle and state changes (pairing, connect/disconnect, owner change, calibration result, recording start/stop) · `debug` detailed flow · `trace` protocol frames (dev only).

## 10. Metrics and observability
- **OpenTelemetry Node SDK** initialised first; **OTLP HTTP exporter** for traces + metrics, 30 s interval, **no-op unless `OTEL_EXPORTER_OTLP_ENDPOINT` is set**.
- **Prometheus exporter enabled by default** (`/metrics`), so a home setup gets metrics without a collector; key metrics also shown on the hub's System page.
- **Automatic instrumentation:** HTTP server (request rate, errors, duration by route + status → free RED metrics), WebSocket, SQLite, outbound HTTP.
- **Tracing:** spans across browser command → hub → tank ack (command latency breakdown).
- **Business metrics:** one `MetricsService` wrapping the OTel Meter with typed `trackX(...)` methods; values bucketed into cardinality-safe ranges; `tankId` allowed as a label (few tanks).
